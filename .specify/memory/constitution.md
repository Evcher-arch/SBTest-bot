# Конституция демо-стенда «ИИ-помощник по внутренним процессам»

Источники требований: `Архитектурное_решение.md` (целевая архитектура) и
`07_План_демо-стенда.md` (упрощения и состав стенда). При расхождении между ними
для стенда действует план, а принципы ниже обязательны в любом случае.

## Core Principles

### I. Права проверяет система, а не модель

- Каждый вызов инструмента от имени сотрудника MUST выполняться с его токеном.
- Сотрудник, от чьего имени идёт вызов, MUST NOT передаваться параметром инструмента:
  MCP-сервер берёт его только из токена.
- Решение о доступе MUST принимать заглушка системы по своей ролевой модели и поиск
  по фильтру групп. Промпт не является средством разграничения доступа.
- Токен MUST NOT попадать в промпт, историю диалога, логи и Langfuse.
- Сервисные выборки MUST быть доступны только сервисной учётной записи рекомендаций
  и MUST NOT входить в список инструментов агента.

Обоснование: ошибка или обман модели не должны открывать чужие данные.

### II. Модель предлагает, код исполняет

- Модель выбирает инструмент и параметры; вызов MUST исполнять оркестратор после
  проверки параметров по JSON-схеме.
- Изменяющее действие (`sd_create_ticket`) MUST исполняться только после нажатия
  кнопки подтверждения, обработанного оркестратором. Текст в сообщении, странице или
  обращении подтверждением не считается.
- Изменяющее действие MUST иметь ключ идемпотентности: повторное подтверждение
  не создаёт дубль.
- Инструмент «выполнить произвольный запрос» MUST NOT существовать. Число шагов агента
  и время вызова MUST быть ограничены конфигурацией.

Обоснование: внедрённая в данные инструкция не должна запускать действие.

### III. Ответ только по источникам

- Ответ о процессе MUST опираться только на найденные фрагменты и содержать ссылку
  и дату обновления страницы.
- Статусы MUST браться только из ответов инструментов в момент вопроса; данные систем
  не копируются и не кэшируются между запросами.
- Если источника нет, помощник MUST прямо сказать об этом и предложить создать обращение.
- Фильтр по группам сотрудника MUST применяться до передачи фрагментов модели.

Обоснование: проверяемость ответа важнее его полноты.

### IV. Рекомендации определяют правила

- Условие, получателя и расписание рекомендации MUST задавать конфигурация правила.
- Модель MUST использоваться только для формулировки текста готового сигнала.
- Повторная отправка одного сигнала MUST отбрасываться; отключённое сотрудником правило
  MUST NOT срабатывать для него.

Обоснование: рекомендации должны быть объяснимы и воспроизводимы.

### V. Границы сервисов и заменяемость

- Оркестратор MUST обращаться к системам только через MCP-серверы; прямые вызовы REST
  API систем из оркестратора запрещены.
- Заглушка системы MUST повторять контракт инструментов из раздела 5.5 архитектурного
  решения, чтобы замена заглушки на реальную систему не затрагивала агента.
- Модель, адреса сервисов, расписания и пороги MUST задаваться конфигурацией,
  а не кодом.
- Ошибки MUST возвращаться в едином виде `error: {code, message}` с кодами `forbidden`,
  `not_found`, `invalid_input`, `unavailable`.

Обоснование: стенд — прототип целевой архитектуры, а не отдельный продукт.

### VI. Трассируемость в Langfuse

- Каждое сообщение сотрудника MUST порождать трассу с шагами: вызовы модели, поиск,
  вызовы инструментов, ожидание подтверждения, ошибки.
- Трассы одного диалога MUST объединяться в сессию; оценка сотрудника MUST
  прикрепляться к трассе.
- Недоступность Langfuse MUST NOT останавливать обработку запроса.

Обоснование: Langfuse — единственная сквозная функция стенда, по ней судят о качестве.

### VII. Только синтетические данные

- В стенде MUST использоваться только вымышленные сотрудники, клиенты, счета,
  обращения и регламенты.
- Секреты MUST храниться в `.env`, который не попадает в репозиторий; в репозитории
  лежит только `.env.example`.
- Бот MUST предупреждать пользователя не вводить реальные сведения.

Обоснование: запросы уходят во внешнюю LLM, анонимайзера и фильтров в стенде нет.

### VIII. Простота и воспроизводимость показа

- Стенд MUST подниматься одной командой `docker compose up` на машине с Docker
  и заполненным `.env`.
- Исходное состояние данных MUST восстанавливаться одним вызовом сброса; даты
  в тестовых данных MUST задаваться относительно текущего дня.
- Компонент, отсутствующий в плане стенда (анонимайзер, фильтры, шлюзы, аудит,
  mTLS, несколько экземпляров), MUST NOT добавляться без поправки к плану.
- Из двух решений выбирается то, в котором меньше кода и контейнеров.

Обоснование: цель — показать сценарии пилота, а не построить промышленный сервис.

## Технологические ограничения

- Язык: Python 3.12 или новее. Веб-сервисы на FastAPI, бот на aiogram 3 (long polling),
  MCP-серверы на FastMCP поверх HTTP.
- LLM и эмбеддинги: OpenAI API; имена моделей задаются переменными окружения.
- Хранилища: PostgreSQL с pgvector (история, правила, подписки, индекс), Redis (сессии,
  токены, ожидающие подтверждения действия), SQLite внутри заглушки систем.
- Развёртывание: Docker Compose; Langfuse — отдельным compose-файлом либо Langfuse Cloud.
- Идентификация: JWT (HS256) сроком до 10 минут, выпускается ботом для выбранного
  демо-пользователя.
- Язык интерфейса, промптов, тестовых данных и документации — русский; идентификаторы
  в коде — английские.
- Нефункциональные цели: индикатор набора сразу после сообщения, полный ответ
  не позже 20 секунд.

## Процесс разработки и критерии качества

- Работа ведётся по циклу Spec Kit: спецификация, план, задачи, реализация. Каждая
  фича — в отдельной ветке и каталоге `specs/`.
- Каждый инструмент агента и каждая сервисная выборка MUST иметь контрактный тест
  на схему входа и ответа.
- Для каждой системы MUST существовать тест «чужой доступ», который ожидает `forbidden`.
  Провал такого теста блокирует слияние.
- Сценарий создания обращения MUST иметь тесты: без подтверждения действие
  не выполняется; повторное подтверждение не создаёт дубль.
- Тестовый набор вопросов хранится в Langfuse и прогоняется перед показом; порог —
  не менее 85 % корректных ответов.
- Тесты не обращаются к OpenAI и Telegram: внешние вызовы подменяются.
- Фича считается готовой, когда её шаг сценария показа проходит после сброса данных.

## Governance

- Конституция имеет приоритет над планами, задачами и привычными практиками. План,
  который нарушает принцип, MUST либо быть исправлен, либо содержать явное обоснование
  отступления в разделе проверки конституции.
- Поправку вносит владелец проекта командой `/speckit-constitution`; поправка
  фиксируется отдельным коммитом с описанием причины.
- Версионирование семантическое: MAJOR — удаление или переопределение принципа;
  MINOR — новый принцип или раздел; PATCH — уточнение формулировок.
- Соответствие проверяется дважды: при составлении плана фичи и перед слиянием ветки.
