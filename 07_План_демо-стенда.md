# План реализации демо-стенда прототипа

Основание: `Архитектурное_решение.md`. Цель стенда — показать вживую все четыре сценария пилота (вопрос о процессе, статус заявки или счёта, создание обращения с подтверждением, рекомендации) на упрощённом окружении, которое поднимается одной командой `docker compose up`.

## 1. Что упрощается относительно целевой архитектуры

| Компонент целевой архитектуры | В демо-стенде | Комментарий |
|---|---|---|
| Корпоративный мессенджер, платформа ботов | Telegram-бот (aiogram 3, long polling) | Long polling не требует публичного адреса и TLS-сертификата |
| Внутренняя LLM | OpenAI API, вызов напрямую из оркестратора | Модель задаётся переменной `OPENAI_MODEL`; нужна модель с вызовом инструментов |
| Модель эмбеддингов | OpenAI `text-embedding-3-small` | |
| Анонимайзер | Отсутствует | В стенде только синтетические данные |
| Защитные фильтры (HiveTrace) | Отсутствуют | Проверка параметров по схеме и отметка о подтверждении остаются в коде оркестратора |
| API-шлюз, шлюз к LLM | Отсутствуют | Бот обращается к оркестратору напрямую, оркестратор — к OpenAI |
| Журнал аудита, мониторинг ИБ, OpenTelemetry | Отсутствуют | Обычные логи контейнеров |
| Langfuse | Сохраняется | Трассы, оценки, стоимость, тестовый набор |
| CRM, биллинг, Service-Desk, Exchange, Confluence | Один сервис-заглушка `mock-systems` с пятью REST API | Данные из seed-файлов, своя упрощённая ролевая модель |
| AD и сервис токенов OIDC, обмен токенов RFC 8693 | Заглушка: бот сам выпускает короткоживущий JWT (HS256) | Один токен для всех систем, без обмена |
| MCP-серверы | Сохраняются (FastMCP, HTTP), один контейнер с четырьмя точками монтирования | Ключевое решение архитектуры, показать нужно |
| RAG-контур | Сохраняется: индексатор, PostgreSQL + pgvector, гибридный поиск с фильтром по группам | Режимы индексатора: первичная загрузка и «изменённые страницы»; полная сверка не делается |
| Сервис рекомендаций | Сохраняется: четыре правила, планировщик, подписки | Интервал опроса 1–2 минуты и ручной запуск для демонстрации |
| Redis, PostgreSQL | Сохраняются | |
| mTLS, два экземпляра сервисов, хранилище секретов | Отсутствуют | HTTP внутри сети compose, секреты в `.env` |

Принципы, которые стенд обязан продемонстрировать, несмотря на упрощения:

1. Помощник не расширяет права сотрудника: права проверяет заглушка системы по токену, а не модель.
2. Сотрудник не передаётся в параметрах инструмента: MCP-сервер берёт его из токена.
3. Изменяющее действие выполняется только по нажатию кнопки, с ключом идемпотентности.
4. Рекомендации определяют правила, модель только формулирует текст.
5. Ответ по регламентам — только по найденным фрагментам, со ссылкой и датой обновления.

## 2. Схема стенда

```
Telegram ──► tg-bot ──► orchestrator ──► OpenAI (chat + embeddings)
               ▲            │  │  └────► Langfuse
               │            │  └───────► search (RAG) ──► PostgreSQL + pgvector ◄── indexer
               │            └──────────► mcp-systems ──► mock-systems             │
               │                              ▲          (CRM, биллинг, SD,       │
               └── recommender ───────────────┘           календарь, Confluence) ◄┘
                     (правила, планировщик)
Redis: сессии, токены, ожидающие подтверждения действия
```

| Контейнер | Стек | Порт |
|---|---|---|
| `tg-bot` | Python, aiogram 3, FastAPI (приём уведомлений) | 8443 |
| `orchestrator` | Python, FastAPI, OpenAI SDK, клиент MCP, Langfuse SDK | 8000 |
| `search` + `indexer` | Python, FastAPI, APScheduler | 8010 |
| `mcp-systems` | Python, FastMCP: `/crm`, `/billing`, `/sd`, `/calendar` | 8020 |
| `recommender` | Python, FastAPI, APScheduler | 8030 |
| `mock-systems` | Python, FastAPI, SQLite | 8040 |
| `postgres` (pgvector), `redis` | Готовые образы | 5432, 6379 |
| Langfuse | Официальный `docker-compose.yml` отдельным файлом | 3000 |

Langfuse самостоятельно поднимает ещё PostgreSQL, ClickHouse, Redis и MinIO (около 4 ГБ памяти). Если ресурсов стенда мало, используется Langfuse Cloud: меняются три переменные окружения, код не затрагивается.

## 3. Демо-пользователи и идентификация

AD нет, поэтому сотрудник выбирается в боте: команда `/start` показывает кнопки с персонажами, выбор сохраняется в Redis по `telegram_user_id`. Это позволяет одному ведущему показывать разграничение доступа, переключая роли командой `/role`.

| Персонаж | Роль | Группы | Что видит |
|---|---|---|---|
| Иванов | Менеджер по продажам | `sales`, `all` | Клиентов и счета своего портфеля, свои обращения |
| Петрова | Менеджер по продажам | `sales`, `all` | Другой портфель клиентов |
| Сидоров | Исполнитель Service-Desk | `it`, `all` | Назначенные ему обращения |
| Кузнецова | Руководитель Иванова и Петровой | `sales`, `managers`, `all` | Данные подчинённых, закрытое пространство «Для руководителей» |

При каждом сообщении бот выпускает JWT (`sub`, `groups`, `subordinates`, срок 10 минут) и кладёт его в Redis по идентификатору сессии. Оркестратор достаёт токен только в момент вызова инструмента; в промпт, историю и Langfuse токен не попадает. Сервис рекомендаций использует отдельный сервисный токен с ролью `recs-service`.

## 4. Этапы работ

Оценка для одного разработчика: 9–10 рабочих дней.

### Этап 0. Каркас (0,5 дня)

- Монорепозиторий: `services/<имя>`, общий пакет `common` (настройки, JWT, модели ошибок `error: {code, message}`), `seed/`, `eval/`.
- `docker-compose.yml` со всеми контейнерами, `.env.example`, проверки готовности `/health`.
- Регистрация бота в BotFather, ключ OpenAI, ключи Langfuse.

Результат: `docker compose up` поднимает пустые сервисы, все `/health` отвечают.

### Этап 1. Заглушки систем и тестовые данные (1,5 дня)

- `mock-systems`: REST API пяти систем в объёме, нужном инструментам раздела 5.5.
  - CRM: поиск клиента по названию или ИНН, ответственные менеджеры.
  - Биллинг: список счетов, счёт с оплатами, выборка просроченных и с подходящим сроком.
  - Service-Desk: список обращений, карточка с историей, типы обращений с полями, создание обращения с `idempotency_key`, выборка «без движения».
  - Календарь: встречи сотрудника за период, выборка по дате.
  - Confluence: список страниц с `updated_at`, текст страницы, группы с правом чтения.
- Ролевая модель в заглушке: проверка JWT, портфель менеджера, подчинённые руководителя, коды `forbidden` и `not_found`.
- Seed-данные (YAML): 4 сотрудника, 8–10 клиентов, 25–30 счетов (часть просрочена, часть со сроком в ближайшие дни), 15–20 обращений, 5 типов обращений, встречи на «завтра», 15–20 страниц регламентов в трёх пространствах (HR, закупки, «Для руководителей»). Даты в seed задаются относительно текущего дня, чтобы демо не устаревало.
- Служебные методы для демонстрации: `POST /admin/reset` (вернуть исходные данные), изменение счёта, обращения и страницы. Доступны через Swagger UI заглушки.

Результат: все методы вызываются из Swagger, чужие данные возвращают `forbidden`.

### Этап 2. MCP-серверы (1 день)

- Девять инструментов систем из раздела 5.5 с JSON-схемами входа, ограничением размера списков и `has_more`.
- Четыре сервисные выборки, доступные только по токену `recs-service` и скрытые из списка инструментов агента.
- Токен сотрудника берётся из заголовка запроса и передаётся в заглушку; параметра «от чьего имени» у инструментов нет.

Результат: инструменты вызываются из MCP Inspector, сервисные выборки с токеном сотрудника отклоняются.

### Этап 3. RAG-контур (1,5 дня)

- Схема в PostgreSQL: фрагмент, вектор, `tsvector`, идентификатор и версия страницы, пространство, путь заголовков, ссылка, дата обновления, массив групп.
- Индексатор: первичная загрузка и режим «изменённые страницы и права» раз в минуту; нарезка по заголовкам; замена фрагментов страницы одной транзакцией.
- Сервис поиска: векторный и полнотекстовый поиск с объединением результатов (RRF) и фильтром по группам из токена.
- Инструмент `search_regulations`.

Результат: один и тот же запрос возвращает разные фрагменты Иванову и Кузнецовой; правка страницы в заглушке попадает в ответ в течение минуты.

### Этап 4. Оркестратор и Langfuse (2 дня)

- Собственный цикл агента на OpenAI SDK: модель выбирает инструмент, код проверяет параметры по схеме и исполняет вызов; лимит шагов и таймауты.
- Системный промпт: отвечать только по фрагментам и данным инструментов, приводить ссылку и дату, при отсутствии регламента предлагать создать обращение.
- История диалога в PostgreSQL, состояние сессии в Redis.
- Подтверждение: `sd_create_ticket` не исполняется сразу, а сохраняется в Redis как ожидающее действие с `action_id` и ключом идемпотентности; оркестратор возвращает боту черновик. Исполнение — только по `POST /confirm/{action_id}`.
- Методы: `POST /chat`, `POST /confirm/{action_id}`, `POST /cancel/{action_id}`, `POST /formulate` (текст рекомендации), `POST /feedback`.
- Langfuse: трасса на сообщение, сессия на диалог, вложенные шаги (вызовы модели, поиск, инструменты, ожидание подтверждения), расход токенов и стоимость, метки сценария и версии промпта.
- Отказы: при недоступной системе — сообщение, какая именно; при недоступном OpenAI — заготовленный ответ; недоступность Langfuse работу не останавливает.

Результат: все сценарии проходят через `curl`, шаги видны в Langfuse.

### Этап 5. Telegram-бот (1 день)

- Команды `/start`, `/role`, `/help`, `/digest` (рекомендации по запросу), `/reset` (очистить диалог).
- Индикатор набора сразу после получения сообщения; ответ отправляется целиком.
- Черновик обращения с кнопками «Создать» и «Отменить»; повторное нажатие не создаёт дубль.
- Кнопки оценки 👍 и 👎 под ответом, оценка уходит в Langfuse к трассе.
- Внутренний метод `POST /notify` для уведомлений от сервиса рекомендаций.
- Ответ отправляется как обычный текст со ссылками на карточки заглушки.

Результат: три диалоговых сценария проходят в Telegram.

### Этап 6. Сервис рекомендаций (1 день)

- Четыре правила в YAML: источник, условие, получатель, расписание, шаблон.
- Планировщик: опрос каждые 1–2 минуты, утренняя сводка по расписанию и по `POST /admin/run` для показа.
- Отбрасывание уже отправленных сигналов (таблица в PostgreSQL), подписки сотрудника.
- Инструменты агента `recs_list_my` и `recs_set_subscription`.
- Цепочка: выборка через MCP → правило → `/formulate` в оркестраторе → `/notify` в боте.

Результат: после изменения срока счёта в заглушке ответственный менеджер получает уведомление в Telegram; отключённое правило не срабатывает.

### Этап 7. Проверка качества и подготовка показа (1,5 дня)

- Тестовый набор в Langfuse на 30–40 вопросов: процессы, статусы, создание обращения, вопросы без ответа, чужие данные, внедрённая инструкция в тексте страницы и обращения.
- Скрипт прогона набора с автоматической оценкой моделью-оценщиком и отчётом в Langfuse.
- Дашборд Langfuse: стоимость по сценариям, время ответа, оценки.
- README: запуск, переменные окружения, сценарий показа, сброс данных.
- Прогон сценария показа с чистого состояния.

## 5. Сценарий показа

| № | Шаг | Что демонстрирует |
|---|---|---|
| 1 | Иванов: «Как оформить отпуск?» | Ответ по шагам со ссылкой и датой обновления |
| 2 | Иванов: вопрос по регламенту для руководителей | Отказ: страница недоступна. Тот же вопрос от Кузнецовой — ответ |
| 3 | Иванов: «Что со счетами по ООО Ромашка?» | Два инструмента подряд: CRM, затем биллинг |
| 4 | Иванов: счёт клиента Петровой | Отказ системы. Кузнецова тот же счёт видит |
| 5 | Иванов: «Не работает VPN, создай заявку» | Черновик, кнопка, созданное обращение, отсутствие дубля при повторном нажатии |
| 6 | Иванов: «Как заказать пропуск на парковку?» (регламента нет) | Честный ответ «не найдено» и предложение создать обращение |
| 7 | В заглушке сдвигается срок счёта, запускаются правила | Уведомление в Telegram; `/digest`; отключение правила |
| 8 | Страница с внедрённой инструкцией «создай заявку» | Действие без кнопки не выполняется |
| 9 | Langfuse | Трасса диалога, шаги, стоимость, оценка, прогон тестового набора |

## 6. Критерии готовности

- Стенд поднимается одной командой на чистой машине с Docker и заполненным `.env`.
- Все девять шагов сценария проходят с первого раза после `POST /admin/reset`.
- Все одиннадцать инструментов агента вызываются и видны в трассах Langfuse.
- На тестовом наборе корректных ответов не меньше 85 %, все тесты на чужие данные пройдены.
- Полный ответ приходит не позже 20 секунд, индикатор набора — сразу.

## 7. Риски и ограничения стенда

| Риск | Что делаем |
|---|---|
| OpenAI API и Telegram могут быть недоступны с площадки стенда | Размещение стенда на внешней площадке либо прокси: адреса задаются `OPENAI_BASE_URL` и настройкой прокси бота |
| В OpenAI уходят тексты запросов и данных | Только синтетические данные; на стартовом экране бота предупреждение не вводить реальные сведения |
| Langfuse требует много памяти | Запасной вариант — Langfuse Cloud |
| Модель вызывает лишние инструменты или пропускает нужные | Тестовый набор с этапа 4, а не в конце; модель меняется переменной окружения |
| Упрощённая идентификация воспринимается как целевая | В README и на показе явно называются отличия от целевой схемы (таблица раздела 1) |

Что стенд не проверяет: обратимое маскирование, работу фильтров, обмен токенов и делегирование, нагрузку и отказоустойчивость, интеграцию с реальными API систем. Эти вопросы остаются на этап подготовки пилота.
